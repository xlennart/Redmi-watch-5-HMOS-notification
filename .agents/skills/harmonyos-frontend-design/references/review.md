# 评审与验证

先确认目标任务、可用代码/截图/录屏、设备/API 和未明确的假设。已有用户授权时直接推进对应改动；用户只要审查时输出发现。

依次关注关键任务与返回路径、窗口与输入适配、真实状态、层级与令牌、动效连续性、无障碍。只报告有证据的缺陷，避免为了全面而制造问题。

| 优先级 | 使用条件 |
|---|---|
| 严重 | 关键任务不可操作、结果错误、主要内容截断或重要操作无法访问 |
| 重要 | 明显影响使用，应该在交付前修复 |
| 一般 | 局部一致性或表现问题 |
| 建议 | 可选改进，或依赖尚缺的运行证据 |

每条发现写清：文件/区域/时间点、触发条件、用户影响、来源是项目要求还是官方指导、最小修复。API 不确定或只有静态推断时标出待验证，不凭语气判定阻塞。

验证选择与任务相称，不要求每次都开展全部专项：

| 产物 | 有意义的检查 |
|---|---|
| HTML | 真实浏览器首屏与滚动、窄宽窗口、主题、长文本、焦点、键盘、主要交互、空/错误状态；检查控制台 |
| ArkUI | 目标工程构建；相关设备或模拟器上的输入/返回/状态/布局；动效变更再看快速重复和打断 |
| 令牌 | JSON 可解析、导出消费一致、重要文字和操作色的对比度、主题切换 |
| 截图还原 | 对应画布下并排或叠图对照；标识不可读文案、缺失资源及推断 |

报告哪些环境已检查、实际结果及限制。未运行的 API/设备行为明确保留待验证。不要将“风格相似”当作平台规范符合的唯一证据。
