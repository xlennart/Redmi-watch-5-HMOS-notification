# 手机实况窗与小米超级岛：外卖进度同步研究

2026-10-13。用户优先希望在手表查看外卖进度，并补充小米侧功能名称为“小米超级岛”。本轮研究与观测准备，不宣称已实现超级岛或完整实况窗卡片。

## 已确认的入口与限制

小米官方将超级岛定义为焦点通知的升级，HyperOS 2 对应焦点通知、HyperOS 3 对应超级岛，外卖属于官方支持的业务场景。客户端通过 Android 通知 extras 中的 `miui.focus.param` 及模板参数发布；它是业务应用发布自身动态服务信息的能力，不能直接作为鸿蒙应用读取其他来源或 Redmi Watch 5 显示卡片的接口。

来源：[业务介绍](https://dev.mi.com/xiaomihyperos/documentation/detail?pId=2140)、[版本范围](https://dev.mi.com/xiaomihyperos/documentation/detail?pId=2141)、[开发指南](https://dev.mi.com/xiaomihyperos/documentation/detail?pId=2131)。本机是 HarmonyOS，不能把这些 Android extras API 当作可调用的鸿蒙接口。

鸿蒙 Live View Kit 用于实况窗的创建、更新、结束和按 ID 查询；API 26 另有由来源应用提供的 `shareUrl` 分享链接。已核对的公开 SDK 中没有供普通应用枚举并订阅其他应用完整实况窗数据的通用接口。分享链接不是访问其他应用订单数据的授权，也不等同于手表蓝牙协议。

来源：[Live View Kit](https://developer.huawei.com/consumer/cn/sdk/live-view-kit)、[HarmonyOS 7 实况窗分享说明](https://developer.huawei.com/consumer/cn/doc/guidebook/solution-0000002784570841)。具体字段以本机 API 26 的 `@hms.core.liveview.liveViewManager.d.ts` 为证据；未申请创建自身实况窗的权益，因为这不能解决读取其他应用订单的问题。

当前已获准的通知订阅回调 `NotificationInfo` 包含来源、通知标识、通知类别、时间和 `NotificationExtensionContent`；后者仅定义标题和正文，没有卡片模板、进度数值、图片、按钮或订单对象。实况类别 `SlotType.LIVE_VIEW` 的枚举值为 4。是否会向本应用投递某家外卖应用的实况类别通知、文字是否包含有用进度，仍需该来源在真实业务中验证。

## 本轮增加的观测

通知扩展继续只处理系统投递的已授权通知。新增“实况类回调 / 含文字”计数，位于问题排查的传输详情；持久化只保存计数，不保存标题、正文、订单号、地址、截图或完整卡片。自身通知不混入统计，旧存储不会被追溯认定为实况通知。

计数是回调数量，不是唯一订单数量，也不是手表可见提醒数量；“含文字”只证明字段非空，不证明文字包含外卖状态或预计送达时间。普通通知转发器原本即可处理系统提供的标题和正文，队列会合并等待中的相同来源/标识更新；此行为尚未用真实外卖实况窗验收。

## 外卖优先的推进顺序

1. 用户按原系统授权流程允许外卖来源，不增加订单或账号权限。
2. 用户下一次正常使用外卖时，比较实况类计数的变化，并检查手表实际收到的文字；不为测试要求用户下单或分享订单资料。
3. 如果有可用文字回调，先验证“接单、取餐、配送、送达”等阶段可否以普通通知更新展示。需要进一步确认相同通知 ID 在表端是更新同一条、生成新条目还是被忽略；传输 ACK 不替代显示验证。
4. 若文字回调不足，则需要来源应用合作或官方开放的跨应用实况数据接口，不能凭推测解析订单或用屏幕 OCR 当后台桥接。
5. 如后续找到 Redmi Watch 5 对应的动态卡片/进度协议，再研究表端样式与交互。当前项目和已核对的 Gadgetbridge 通知协议证据主要覆盖普通通知文字、标识、应用图标及移除等能力；未找到已验证的超级岛整卡传输入口。这不等于断言固件没有其他能力。

可预先规划的模型为活动标识、来源、阶段文字、更新时间、结束标记，以及“可选且需来源提供”的进度/预计到达时间。当前不伪造这些字段，也不把“创建本应用的实况窗”包装成“读取其他应用的实况窗”。
