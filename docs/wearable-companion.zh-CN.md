# 鸿蒙原生手表管理应用

长期目标：逐步接替小米运动健康，手机独立完成认证、连接、通知与设备管理。当前优先通知；不把“存在协议定义”当作“已支持全部功能”。

## AstroBox 公开模块覆盖

主仓库 [AstroBox-NG](https://github.com/AstralSightStudios/AstroBox-NG) 的 `repos.xml` 明确分开 Core、Pb、Bluetooth、Account、AppWasm、插件系统及部分私有应用模块。本项目已读取公开协议核心、账号模块、protobuf 定义，以及 TatumRobotics/BandBurg；未访问私有仓库。

| 功能 | 公开参考 | 本项目状态与后续工作 |
| --- | --- | --- |
| 认证、连接 | Core auth、SAR、L1/L2、cipher；Account xiaomi | Redmi Watch 5 认证已验证；日志可用，新增账号 Cookie 服务交换待验证 |
| 通知 | Core NotificationSystem、wear_notification | 固定提醒已显示；新增通知扩展串行转发及开启/停止开关，继续验收真实消息和锁屏 |
| 手机音乐遥控 | wear_media PlayerInfo / PlayerControl | 预留手机媒体适配与手表双向事件接口；播放/暂停/切歌/音量与歌曲状态各自映射 |
| 手表本地音乐 | Core MediaSystem、MassSystem | 列表、曲库与文件传输是另一项服务，不能用音乐传输实现冒充手机音乐控制 |
| 电量、固件、设备信息 | Core InfoSystem / DeviceData | 通用设备信息接口已预留，未新增实际查询 |
| 时间、语言及通知设置 | Core SyncSystem、wear_system | 当前只实现通知类别配置读写；时间与语言接口预留 |
| 睡眠、活动、运动 | wear_fitness、文件数据通道 | 已有统一分页健康模型；目标固件读取、单位映射及独立存储待实现 |
| 表盘、快应用 | Core WatchfaceSystem / ThirdpartyAppSystem / Install / Mass | 预留资源服务；需要容量、分片确认、取消与文件类型校验 |
| 天气、闹钟、日历、联系人 | 对应 Pb 协议 | 后续增加独立服务及授权边界，当前不读通讯录或日历 |
| 蓝牙网络 | Core NetworkSystem、平台 tun/dhcp | 未来能力候选，依赖鸿蒙网络能力和目标固件，当前不启用 |

手机音乐控制的鸿蒙入口已从本机 API 26 SDK 核对：`avSession.getAllSessionDescriptors()` 和 `createController()` 需要 `MANAGE_MEDIA_RESOURCES` 或 `MANAGE_MEDIA_RESOURCES_FOR_PUBLIC`；不能仅凭蓝牙握手就控制其他应用。当前不申请这些权限，也不默认卓易通播放器能暴露鸿蒙媒体会话。

## 代码边界

`core/WearableServices.ets` 定义统一设备适配器、连接状态、通知发送/撤销、音乐状态/控制、设置、资源传输及能力证据；`WearableData.ets` 继续承载健康模型。这些是可编译契约，不是已经实现的功能。

连接层负责 SPP、分帧、确认、超时、加密和断开清理；设备协议层负责命令及字段映射；功能层负责通知、音乐、健康等服务；鸿蒙适配层负责通知扩展、媒体会话、权限和生命周期。页面只依赖能力与服务结果，未来不得为每个功能各建一条蓝牙连接。

当前通知转发复用已验证的认证/发送会话，每条消息按需连接，扩展内串行处理。后续将该会话抽为单一连接所有者及命令路由器，再加入保持连接、重连与双向音乐事件。不能在没有稳定性证据时声称当前实现已是常驻连接。

每项能力分别记录协议已知、目标设备支持、手机授权、实现状态和真机验收。健康未知值不补零；传输 ACK 不等于可见送达；音乐操作失败不模拟播放状态；未提供的可选服务不显示为可用。

## 本轮通知实现

- 开启时校验手表、认证材料和系统通知授权，保存本机目标与开关；关闭时清空待发队列并取消当前会话。
- 只接收系统授予的通知，过滤自身应用；正文只在内存中处理，不写入文件或日志。
- 16 条有界队列；相同来源/通知的待发更新替换旧条目，取消通知移除待发条目；超过一分钟的积压跳过。
- 标题/正文按 UTF-8 限制大小，保留中文与 emoji；每次发送重新认证与检查通知配置。失败不盲目重发。
- 只持久化收包、失败、跳过计数和错误码。当前不保证取消已显示的手表提醒；传输中取消也不保证撤销已发帧。

验收顺序：自有固定测试源实际转发 → 用户授权应用真实通知 → 停止与权限撤销 → 锁屏、退到后台、断线重连与重启 → 通知稳定后音乐控制 → 健康数据与设备管理逐项启用。账号路线继续优化，但不阻断日志认证后的功能开发。
