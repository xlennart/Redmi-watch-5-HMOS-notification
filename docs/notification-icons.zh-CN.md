# 通知来源应用图标

## 本轮实现与验证边界

### 2026-10-13 用户反馈与跨应用权限

用户确认固定测试已显示腕间通知自身图标，但华为支付等原生应用通知仍显示默认图标。针对系统已允许订阅的华为钱包、华为支付做应用内资源读取诊断，两者都在 `bundleManager.getBundleInfoSync` 返回 `201`，尚未进入像素读取或上传。这是资源访问被系统拒绝，不能归因于卓易通。

本机 SDK 的 `GET_BUNDLE_INFO` 为 normal / system_grant，且 `provisionEnable=true`；清单声明不能证明实际授予。尝试通过官方 CLI 的调试 Profile 请求补入该 ACL，服务端明确拒绝“permission not in support scope”。原签名材料已从备份恢复并逐字节比对。没有提交或安装修改后伪造的 Profile，没有改动手机系统签名/权限策略。

问题排查页现在直接查询当前访问令牌的该权限，显示来源图标读取是否获许可；连接在图标协商前失败时保留最近一次具体图标结果。普通开发者的当前签名路线尚不能读取其他应用图标，后续可评估带来源记录的离线图标库或由用户在手机选择图片的映射，不能承诺它们会自动获得任意应用的实时图标。

### 2026-10-13 真机协商定位

用户反馈应用内测试仍显示默认图标。手机诊断实际记录 `unsupported / format_2_size_176`：Redmi Watch 5 请求格式 2、边长 176，本项目的 128 像素和 64 KiB 上限使其在上传前就被拒绝。现允许最大 256 像素、256 KiB 原始数据，176×176 BGRA 为 123904 字节；MASS 长度、封包与分片统一使用该上限，上传调度预算增加至 30 秒。新增完整重组和 CRC 校验测试覆盖真实协商值及超限拒绝。

本应用测试直接取编译后的 `app.media.app_icon`；PixelMap 在读取前明确转换到 BGRA，避免缺失应用元数据或颜色格式不匹配。只记录图标阶段、原因枚举和完成时间，不保存图像。安装后的固定测试记录 `uploaded / transport_ack`，随后用户确认自身图标实际显示。该结果仅覆盖自身来源；其他应用仍未通过。

### 2026-10-12 官方 APK 对照修订

用户提供的静态分析报告指出，小米运动健康经 `7/15` 协商后把图标作为独立文件传输。本次以同一 APK（版本 3.59.1，SHA-256 `46100649d47000e8886d94cfbb34c18706e492a5d3aaa7f34cd4785841ffc254`）再次核查实际文件编码，没有执行 APK，也没有复制反编译源码进仓库。

发现并修复三项协议/格式差异：

- 官方 `oli.j` 写入应答 protobuf 时会省略值为 0 的可选格式字段 2。旧实现把缺省值读成未知格式 `-1`，因此合法 RGB565 协商会被直接跳过。现仅在字段缺省时采用协议默认值 0；字段存在但类型错误仍拒绝。新测试使用官方实际省略布局完成上传，避免仅用显式写出的零值测试。对应静态证据为 `ev_39ba5dbe7de333c68dfb58b4e5ae4c195273d83b24de68c7d7cc23d1b42bb344`。

- 格式 8 的官方文件是 **RGB565 大端字节序加 alpha**。旧实现按红蓝交换的 ABGR565 小端写出，现改为 RGB565 BE；格式 7 继续使用 RGB565 LE 加 alpha。新测试使用不相等的红、绿、蓝值区分字节序和通道交换，避免仅靠灰色测试掩盖错误。
- 官方 `IconSendTask.save2File` 对格式 4 也使用 RGB565 原始像素写入。现按该通知图标分支增加格式 4 支持，不根据通用枚举名称猜成 RGB888。新增完整协商/上传测试验证长度为每像素 2 字节。

32 位颜色分支会把 Android 的 RGBA 像素交换红蓝后写为 BGRA，与本项目的格式 2/3 路径一致。RGB565 和带 alpha 的文件直接写原始字节，没有额外的图片宽高头。图标仍保留在内存中，传输后清除；手机来源解析失败时继续使用默认图标并记录安全的阶段/数值错误码。

静态 REA 证据：`IconSendTask.save2File`：`ev_44b5dd497596fef0e3343f982af400af2a064e729029216bd8da4c91e007c8f2`；格式 7 转换 `c13.j`：`ev_2260059d4ecbe93124526944dc727177efb7cfbd485b4167fc3250d765f3d2ac`；格式 8 转换 `c13.i`：`ev_6bf1813185941e08f9fb48ef9850fbdf51f893e9f9e5aecdd7e3fbad3466e820`；32 位转换 `c13.l`：`ev_5866d51e6d77ae2006466933c434d6f195ea6ff67a726e1176c5abd502d870d9`；原始文件写入 `c13.e`：`ev_512088fb0c27af490465fd32d1eac0987b86d181b0e4ab1238598be18b1a507f`。这些证据来自完整方法反编译，不代表手表执行结果。

本次没有实机验证。格式修复不会解决所有来源资源不可访问、卓易通容器图标缺失或固件缓存问题，不能据此宣称手表已显示图标。`DeviceContact.sendFile(3, 2)` 是官方调用层参数，不能直接当成 SPP 的 channel/opcode；本项目继续使用此前公开协议验证的 MASS 类型 50 与 SPP 数据通道，未凭报告摘要替换底层封包。

### 2026-10-07 后续修订

用户确认手表仍未显示来源应用图标，前一版不能视为图标功能验收成功。本次新增以下待实测修复：

- 在发送当前来源通知前主动发送 `7/15` 协商，避免完全依赖手表重复发出 `7/16`。来源仍限制为本次已授权应用，不枚举其他应用。
- `7/15` 回复若含字段 5 的分片长度，直接使用已协商参数上传；字段缺省时才进行独立 MASS prepare，避免忽略图标专属协商。
- 增加 PNG 格式 6；系统在内存中缩放并编码，检查 PNG 签名、尺寸与 64 KiB 上限。原始像素格式仍保留。
- Drawable 读取失败或没有 PixelMap 时尝试原始媒体资源解码；阶段与数值错误码分别记录，不保存原始异常、包名或图像。测试图标结果与后台最近图标结果分别显示。
- 区分 pending、cached、uploaded、unsupported、unavailable、failed。cached 是手表报告已缓存，uploaded 是分片 ACK，二者均不能替代可见图标。

本轮没有执行手机 UI 或手表显示检查；需要后续真实通知验证这些调整。资源不可访问、卓易通容器图标或固件要求其他格式仍可能保留默认图标。

以下保留初版数据路径，后续修订优先于其中的请求方式和格式限制。

用户报告自动转发通知已显示，但所有来源使用默认图标。源码检查发现两个缺口：收到 `7/15`、`7/16` 时仅记录诊断文字，没有回应或上传；自动转发收包后只等待一秒就关闭连接。本轮补齐图标请求处理，未连接手机、未安装或进行手表显示验证。

当前实现是原生应用图标资源上传，不是从通知正文、头像或网络图片中猜图标。通知扩展的 `NotificationInfo` / `NotificationExtensionContent` 只提供来源名称与文本，不提供图标。

## 数据路径

1. 按原流程认证并发送通知。收到文字数据的传输 ACK 后保留连接，自动转发最多等待 4 秒接收后续请求；固定测试保留原有 20 秒观察窗口。
2. 手表发 `NOTIFICATION / APP_ICON_APPLY (7/16)`，其 `Notification` 字段 16 的包名只能匹配当前已授权来源，允许有至少 8 字节的前缀截断。不会按手表任意给出的包名查询其他应用。
3. 回应 `PREPARE_APP_ICON (7/15)`，字段 14 带手表请求的包名，声明不压缩。手表字段 15 的回应指定状态、像素格式和正方形边长。
4. 通过本机 `bundleManager.getBundleInfoSync` 获取该来源的 `iconResource`，通过 `ResourceManager.getDrawableDescriptor(Resource)` 合成普通或分层应用图标。使用 API 26 的 `PixelMap.readPixelsToAreaSync` 读出 BGRA，按实际 alpha 类型处理预乘，保留宽高比缩放。
5. 上传协商使用 `MASS / PREPARE (22/0)`，数据类型 **50（通知图标）**。携带图标 MD5、原始字节长度，并检查手表回应的 MD5、状态、压缩及分片长度。
6. 数据通道使用 SPP v2/v3 的 `channel=2, opcode=1`，按照公开协议传送 `版本0 + 类型50 + MD5 + 长度LE + 像素 + CRC32LE`。分片有总数与当前序号，逐片等待对应序号的 ACK；未增加重试、解绑或任何固件操作。

收到图标分片 ACK 只记为 `uploaded`（收包），不能据此声称已显示。验证详情显示最近一次图标处理状态，持久化中没有图像、通知正文或密钥。

## 限制与回退

- 支持原始像素格式 0 / 1 / 4 RGB565、2 / 3 32 位颜色、7 / 8 带 alpha 的 8565，以及 PNG 格式 6；JPEG、EZIP 等尚未实现，收到此类要求时保留默认图标。
- 图标边长限制为 1–256 像素，来源解码图像每边最多 1024；原始上传不超过 256 KiB，平台 PNG 编码仍限 64 KiB。分片限制在协议会话协商的 4096 字节之内。
- 图标转换与上传设置 30 秒调度预算，写入/ACK 等待另有超时，整个认证会话仍有 60 秒总期限。每个会话只回应当前来源一次，重复请求不会重复上传。停止转发会取消同一个会话。
- 当前只接受从偏移 0 开始的新上传。非零续传偏移、未知压缩、MD5 不一致、非法分片长度及上传失败都会取消已开始的图标上传，保持文字通知的已有收包结果。不同固件的续传长度定义尚未统一验证。
- 图标资源不可访问、应用已卸载或权限不足时保留默认图标，不改写来源身份。应用分身使用该原生应用的基础图标，不保证含分身角标；卓易通等容器内的 Android 图标未必能由原生包资源接口取得。
- 通知构建新增 `ohos.permission.GET_BUNDLE_INFO`，仅查询正在处理的已授权来源，没有枚举已安装应用。实际授权与跨应用图标读取仍需后续真机验证；基础诊断构建不增加该权限。取不到资源时不会阻断文字转发。
- 没有手机图标缓存或在线下载。手表是否缓存图标、是否即时替换当前提醒中的图标以及多次连接后的行为，均尚未验收。

## 离线证据

核心测试覆盖已知颜色/字节序/透明度、宽高比、大小及格式限制、CRC32 标准向量、MD5 与分片重组、模拟手表的完整请求上传、重复/外来/过短包名、缺失资源和上传拒绝/续传/压缩/NACK 回退。鸿蒙 API 26 的原生编译与本机签名另行执行，不等同于真机效果验证。
