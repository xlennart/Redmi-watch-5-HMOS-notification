# 手机音乐控制与本轮验收

## 当前范围

2026-10-12 按用户要求新增手机播放状态同步和手表遥控，不涉及把歌曲上传到手表。通知仍为首页；音乐页面是“设置 → 手机音乐控制”的次级入口，健康、运动、音乐库、账号及其他设备功能不扩展。既有通知界面设计继续适用于首页，本页优先于历史文档里“音乐只保留接口”的描述。

## 实现

- `PhoneMediaAdapter.ets` 通过 API 23+ 的 AVSession 公共控制器选择系统置顶的活动媒体会话，排除本应用及不活动的历史记录。选择结果最多缓存五秒，系统会话事件会使其失效；元数据、播放态与支持命令通过事件更新，避免每次按键重新枚举和创建控制器。进度使用系统实时播放位置。无活动会话、停止或撤权不会沿用上一首标题。
- `WatchMusic.ets` 独立编写 Xiaomi `18/1` 状态与 `18/2` 控制编解码。同步标题、艺术家、播放/暂停/空闲、秒数和音量；接收播放、暂停、上一首、下一首及音量目标。平台先检查播放器开放的控制命令；音量目标与当前百分比比较后只增减一个原生档位。协议证据见[专项核对](music-protocol-research.zh-CN.md)。
- `WatchNotificationRelay` 在开启音乐时保持已认证 SPP v3 连接；通知复用同一会话。发送按数据包串行等待 ACK，接收和原生音乐控制独立执行，不再等待通知图标上传或状态 ACK 结束。关闭音乐恢复原有逐条通知连接方式。初始化连接失败会回滚音乐开关；运行中断每三秒尝试恢复通道，失败的通知不重发。媒体服务调用有三秒超时，关闭后晚到控制器释放而不执行操作。
- 手表控制只接受认证后的加密应用帧；相邻重复帧不重复执行。控制按顺序执行，最多排队八项，排队超过一秒的旧命令丢弃并记录错误，避免延迟操作播放器。状态每 250 毫秒检查变化，播放进度最多每五秒同步，暂停/空闲最多每三十秒同步；控制及手表查询触发同步。状态回传仍受链路带宽和 ACK 延迟影响。
- 音量改用原生 `AVVolumePanel`：仅在腕间通知处于前台且面板已绑定时申请调整，然后读取真实媒体音量，最多等待 600 毫秒。后台或锁屏返回 `-66`，实际音量未变返回 `-67`，不增加成功计数。旧式全局音量接口已删除。前台面板限制高度为 48，避免占满页面挤掉通知内容。
- 音乐使用 Bluetooth 持续任务，系统会显示任务通知。活动标记有时间戳，进程结束后旧标记过期，旧累计收包不能代表当前在线。连接协调器在同一应用进程内共享；不是跨进程租约或重启后自动恢复服务。

页面不展示伪造曲目或成功态。仅展示真实连接阶段、状态收包计数、手机接受控制的计数以及数值错误码。标题、艺术家、媒体会话 ID 和播放 URL 不写磁盘或诊断日志。音乐状态传输 ACK 不等于手表显示，系统接受控制不等于实际切歌或开始播放。

## 构建与权限

默认 `npm run configure:baseline` 保留基础模式；`npm run configure:notifications` 保留已有通知权限范围；`npm run configure:music` 生成通知加音乐模式，注册 Bluetooth 持续任务并增加：

| 权限 | 本机 API 26 定义 | 使用方式 |
| --- | --- | --- |
| `MANAGE_MEDIA_RESOURCES_FOR_PUBLIC` | system_basic、system_grant、ACL 可配置 | 必须包含在官方签名 profile 的 allowed-acls 中，运行时检查 access token；不使用用户弹窗申请 |
| `KEEP_BACKGROUND_RUNNING` | normal、system_grant | Bluetooth 持续任务 |

定义以目标 SDK `toolchains/lib/PermissionDefinitions.json` 与对应 API 声明为准。API 指引见华为[媒体控制器](https://developer.huawei.com/consumer/en/doc/harmonyos-references/arkts-apis-avsession-avsessioncontroller)与[音量管理](https://developer.huawei.com/consumer/en/doc/harmonyos-references/arkts-apis-audio-audiovolumegroupmanager)。编译成功不表示设备授予权限。

本机已由官方 DevEco CLI 生成包含通知和媒体会话两项 ACL 的 profile，沿用原密钥库、别名和证书。材料不上传；其他开发者须独立申请签名。CLI 若在自动化进程因代理出现 TLS 主机名不匹配，应检查该进程的代理变量；本轮通过仅对该进程直连解决，未关闭 TLS 校验或改动系统代理。

公共音量面板要求前台交互，不能据此承诺锁屏调音量；见 [AVVolumePanel 文档](https://github.com/openharmony/docs/blob/master/zh-cn/application-dev/reference/apis-audio-kit/ohos-multimedia-avvolumepanel.md)。播放、暂停与切歌仍使用媒体会话接口。

## 本轮证据

2026-10-13 后续用户确认音乐控制灵敏很多；这说明按键等待链调整已有可见改善，仍不能替代每项命令、播放器和断线场景的验收。用户明确要求实用的后台音量控制，当前前台面板无法满足。再次核对目标 SDK，公开 C 音量管理器只有查询和回调；AVSession 普通控制命令不含音量，`setVolume` 属于投播控制，不是当前手机播放器。系统 `AudioVolumeGroupManager.setVolumeWithFlag` / `adjustSystemVolumeByStep` 属于系统接口，前者会拒绝非系统应用；当前普通调试签名无法据此承诺后台音量。见 [系统音量接口](https://github.com/openharmony/docs/blob/master/zh-cn/application-dev/reference/apis-audio-kit/js-apis-audio-sys.md)。未采用后台隐形面板或伪造播放会话规避限制。

- 2026-10-13 共享核心及原生平台适配 mock 共 74 项测试通过，新增并发等待期间的加密控制路由、取消唤醒所有等待者、会话缓存、音量实际未变拒绝、前台绑定限制及 176 像素图标完整分片检查。
- DevEco / CLT 26.0.0.851、API 26 原生编译、签名与 `hdc install -r` 覆盖安装成功。
- 用户反馈首版音乐反应慢、音量无效；手机统计没有报错，不能证明操作生效。本轮已修复上述等待链和假成功路径，编译、签名并覆盖安装；响应改善待用户重新验收。
- 音量面板初次接入导致正文不显示，随后限制布局并覆盖安装。手机原生布局已读到通知开关、授权、测试和问题排查入口。手表图标可见效果、后台与锁屏、断线恢复及卓易通播放器兼容仍未通过验收。

## 手机测试

1. 打开腕间通知，确认原有手表与认证材料仍在；开启通知转发，让一个已授权的原生手机应用发送新通知，检查手表通知文字及该应用图标。不要用此前已缓存的旧通知判断新图标。
2. 在手机音乐或视频应用开始播放，打开腕间通知“设置 → 手机音乐控制 → 开启音乐控制”。手表打开手机音乐控制页面，依次测试暂停、播放、上一首、下一首；保持腕间通知在前台测试音量。确认两端实际播放状态，不仅看累计计数。“最近控制耗时”仅计解密收到命令至原生执行结束，不含手表按键到手机的传输时间。
3. 音乐控制开启时再发送一条真实通知，验证通知仍到达；然后锁屏复测。若失败，反馈本页连接状态、最近错误码及手机接受控制是否增加，不发送曲目隐私、认证密钥或账号令牌。

关闭通知转发、切换手表、删除认证材料或诊断测试会同时释放音乐连接，需要手动重新开启音乐。仅关闭音乐则保留通知设置。无需解绑、重置手表或删除小米运动健康绑定。
