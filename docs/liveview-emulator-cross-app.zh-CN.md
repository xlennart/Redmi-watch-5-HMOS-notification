# 实况窗跨应用主动读取：API 26 模拟器实验

2026-10-14。用户建议在 DevEco 模拟器中创建可控实况窗，以排除缺少真实活动 ID 的问题。本轮只用虚构内容，未修改或安装真实手机应用，没有使用 REA。

## 结论

在本次 HarmonyOS 7 / API 26 模拟器的普通第三方应用测试中，`liveViewManager.getActiveLiveView(id)` 查询的是调用应用的活动。已知另一应用的准确活动 ID，仍不能通过该方法读取其内容。相同 ID 可以在两个应用中同时存在，调用者只读到自己的对象。

因此，不能把该方法配合高频轮询作为外卖实况的跨应用同步入口。结论限定于本次公开 API、普通应用与模拟器环境，不替代真机或系统级权益的作用域验证，也不否定其他未来开放接口或来源合作方式。

## 实验对象与步骤

- DevEco CLI 启动已有 Mate 90 Pro 模拟器，配置为 HarmonyOS 7.0.0 / API 26；所有 HDC 安装、查询和界面操作明确指定虚拟设备。
- 发布端为独立包 `com.xlennart.wristliveviewsource`；读取端使用项目真实包名 `com.xlennart.wristnotifications`，临时加入查询或自身发布对照代码。
- 发布端活动 ID 固定为虚构测试值 `731042`，场景为 `DELIVERY`，版本 1/2 分别显示“测试阶段 A/B”，进度 20/60。没有真实订单、账号、地址或业务服务端。
- 发布端先创建并查询自己，确认活动有效；读取端再查询同一 ID。随后发布端更新至版本 2，读取端再次查询。
- 增加自身正对照：读取端创建相同 ID，但标题为“腕间自身对照”、内容为“自身阶段 A”。发布端同 ID 的活动同时有效，再分别读取。
- 结束各自测试活动，确认查询不再返回对象。恢复读取端原始源码及基础模式原始应用，不保留实验逻辑在生产代码。

## 实际结果

| 状态 | 调用者 | getActiveLiveView 结果 |
| --- | --- | --- |
| 发布端版本 1 有效 | 发布端 | code 0，返回 ID 731042、sequence 1、测试阶段 A |
| 发布端版本 1 有效 | 腕间通知 | 1003500009：活动不存在 |
| 上述跨应用查询完成后 | 发布端 | code 0，再次读回版本 1，确认活动未消失 |
| 发布端更新版本 2 | 发布端 | code 0，返回 sequence 2、测试阶段 B |
| 发布端版本 2 有效 | 腕间通知 | 1003500009：活动不存在 |
| 腕间通知创建同 ID 自身活动 | 腕间通知 | code 0，读回“腕间自身对照 / 自身阶段 A” |
| 两应用同 ID 活动共存 | 发布端 | code 0，读回“跨应用实况验证 / 测试阶段 A” |
| 两应用同 ID 活动共存 | 腕间通知 | code 0，仅读回“腕间自身对照 / 自身阶段 A” |
| 结束测试活动后 | 对应应用 | 查询不再返回对象，1003500009 |

跨应用查询耗时分别为 75 ms / 37 ms，自身共存查询为 3 ms。这些数字只是本地 API 调用时间，不是外卖状态到手表显示的延迟。实验没有验证通知订阅回调是否包含实况文字，也没有验证小米手表焦点渲染。

系统通知界面实际显示了发布端的“跨应用实况验证 / 测试阶段 A”卡片与进度条，更新后实际显示“测试阶段 B”与更高进度。已检查原生界面树和截图，不仅根据 startLiveView 返回值认定可见。截图、临时 HAP 和运行记录留在本机忽略目录。

## SDK 文档与运行时差异

DevEco CLI 当前官方本地知识库 `liveview-introduction` 的“模拟器支持情况”明确说明本 Kit 支持模拟器，差异包括地理位置提醒、雨雪背景和连续服务按钮。本轮实际创建、更新和显示进一步验证了基础场景；旧 V13 文档中的“不支持模拟器”不能用来否定当前版本。[官方 Live View Kit](https://developer.huawei.com/consumer/cn/sdk/live-view-kit)

初次最小请求在运行时依次返回 401，具体指出缺少 `primary.clickAction`、`primary.layoutData`、进度模板 `nodeIcons`。SDK 中这些属性虽然以可选类型声明，创建具体场景时仍有条件必需项。本轮补齐指向发布端自身的 WantAgent、进度模板和两个节点图标后创建成功，避免将参数错误误判为权限或跨应用限制。

源码与无签名构建配置已恢复。模拟器恢复原始基础模式的腕间通知；真实手机保持原有正式安装包。本次模拟器安装的实验 HAP 未签名，不能将此环境下的服务权益行为泛化到真机发布权限。

## 对后续路线的影响

1. 继续验证已授权的通知订阅是否随外卖实况更新提供有用文字；这与本实验的主动查询是不同入口。
2. 如需完整结构化数据，研究来源应用主动提供的数据/分享接口，或向华为确认是否存在面向第三方穿戴伴侣的跨应用实况同步开放能力。现有 API 签名不能指定源包名，同 ID 共存也证明 ID 不具备全手机唯一性，不能只靠活动 ID 选择其他来源。
3. 小米目标格式与华为数据入口分别推进；即使焦点 protobuf 编码补齐，也不能绕过源数据取得限制。
